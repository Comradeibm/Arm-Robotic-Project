# Project 1: Robotic Arm Kinematics & Path Planning

Program a simulated 6-axis robotic arm to move from Point A to Point B
without colliding with its environment, using Inverse Kinematics, a
collision-free path planner, and a smooth trajectory spline.

This repository has two layers, built to be used together:

1. **`src/` — a standalone, dependency-light Python simulation.** Pure
   NumPy/SciPy/Matplotlib. This is the "brain": FK, IK, collision
   checking, RRT path planning, and quintic trajectory generation. It
   runs immediately with `python3 demo.py` — no ROS installation
   required — and is what was used to validate the math and produce the
   included output plots.
2. **`ros/` — a ROS/Gazebo/RViz integration layer.** URDF, launch file,
   controller config, and two rospy nodes that take the trajectory
   produced by `src/` and actually execute it on a physics-simulated
   (Gazebo) or real robot, and visualize it in RViz. These files are
   ready to drop into a catkin workspace; they are **not run in this
   sandbox** because ROS is not installed here (see "Why two layers"
   below for why that's the right split).


## 1. Quick start (standalone simulation, no ROS needed)

```bash
cd robotic_arm_project
pip install -r requirements.txt --break-system-packages   # or use a venv
cd src
python3 demo.py
```

This will:
1. Define a 6-DOF arm and a spherical obstacle in its workspace.
2. Solve IK for a target point B, rejecting any solution that collides.
3. Run RRT to find a collision-free path in joint space from A to B,
   then shortcut it to a minimal set of waypoints.
4. Fit a quintic spline through the waypoints (zero velocity/acceleration
   at start and end — a smooth start/stop motion).
5. Re-verify the *entire sampled trajectory* (not just the waypoints) is
   collision-free.
6. Write `../output/trajectory.csv`, `arm_path_3d.png`,
   `joint_trajectory.png`, and `arm_motion.gif`.

Each module (`kinematics.py`, `collision.py`, `rrt_planner.py`,
`trajectory_planning.py`) also has a `__main__` self-test at the bottom
you can run individually, e.g. `python3 kinematics.py`.

## 2. The math

### Forward Kinematics
The arm is defined by a standard **Denavit-Hartenberg (DH)** parameter
table (`[theta_offset, d, a, alpha]` per joint, in `SixAxisArm.__init__`).
FK is the product of the 6 per-joint homogeneous transforms:

```
T_end = T1(θ1) · T2(θ2) · T3(θ3) · T4(θ4) · T5(θ5) · T6(θ6)
```

giving the XYZ position and orientation of every joint and the
end-effector for any set of joint angles.

### Inverse Kinematics
Rather than a closed-form solution (which only exists for specific
DH geometries with a spherical wrist), `kinematics.py` uses the
**numerical Jacobian / Damped Least Squares** method (a Levenberg-Marquardt
style solver):

```
dq = Jᵀ (J Jᵀ + λ²I)⁻¹ · e
```

where `J` is the 6×6 geometric Jacobian (computed analytically from the
FK chain, not finite differences) and `e` is the position/orientation
error. The damping term `λ` keeps the solver stable near singularities
(where a plain pseudo-inverse would blow up). This generalizes to *any*
6-DOF DH chain, which matters because the arm's exact link lengths are
just config values in this project.

### Collision Checking
Obstacles are modeled as spheres (`center`, `radius`) — a standard
simplification since any convex obstacle can be bounded by one or more
spheres. Each arm link (the segment between consecutive joint origins
from FK) is treated as a **capsule** (line segment + `link_radius`).
Collision = point-to-segment distance from the obstacle center to a link
segment is less than `link_radius + obstacle_radius`. This is O(links ×
obstacles) per configuration — fast enough to call thousands of times
inside a sampling-based planner.

### Path Planning (collision avoidance)
Straight-line interpolation between two collision-free joint
configurations can still pass *through* an obstacle in between, so
`rrt_planner.py` implements **RRT (Rapidly-exploring Random Tree)** in
6-D joint space:
- Random joint configs are sampled (with goal-biased sampling) and the
  tree is grown toward them, one `step_size` at a time, rejecting any
  step whose straight-line edge is not collision-free (checked by
  substepping and calling the collision checker).
- Once the tree reaches the goal, the resulting jagged path is
  **shortcut**: pairs of non-adjacent waypoints are tested for a direct
  collision-free connection, cutting out everything in between. This
  turns a many-waypoint RRT path into 2-4 waypoints in practice.

Joint-space (rather than Cartesian-space) planning was chosen because
every sampled point is automatically a kinematically valid arm pose (no
per-sample IK needed), and it composes cleanly with the collision
checker above.

### Trajectory Generation (the smooth spline)
`trajectory_planning.py` fits a **quintic (5th-order) polynomial spline**
per joint through the shortcut waypoints, using `scipy.interpolate.BPoly`
with matched position/velocity/acceleration at every waypoint and zero
velocity/acceleration enforced at the first and last waypoint. This
produces the smooth "start at rest, accelerate, decelerate, stop at
rest" motion profile a real robot controller needs (see
`output/joint_trajectory.png` — velocity and acceleration both taper to
zero at the endpoints). `demo.py` then **re-samples the continuous
spline** (not just the original waypoints) and re-checks it against the
collision checker, since a spline can in principle bulge slightly off
the straight-line waypoint path.

## 3. ROS / RViz / Gazebo integration

The `ros/` folder is a ready-to-drop-in set of files for a catkin
package (suggested name: `six_dof_arm_description`). It was **not run in
this sandbox** — there's no ROS installation or GUI display available
here — but every number in it (link lengths, joint limits) matches the
DH table in `src/kinematics.py`, and the nodes are written against
standard, stable ROS APIs (`actionlib`, `FollowJointTrajectoryAction`,
`control_msgs`, `trajectory_msgs`) that don't change across minor ROS
versions.

### Setup (on a machine with ROS Noetic + Gazebo installed)
```bash
# 1. Create a catkin package and copy files in
cd ~/catkin_ws/src
catkin_create_pkg six_dof_arm_description rospy std_msgs geometry_msgs \
    control_msgs trajectory_msgs actionlib gazebo_ros

cp -r robotic_arm_project/ros/urdf      six_dof_arm_description/
cp -r robotic_arm_project/ros/launch    six_dof_arm_description/
cp -r robotic_arm_project/ros/config    six_dof_arm_description/
cp -r robotic_arm_project/ros/srv       six_dof_arm_description/
cp -r robotic_arm_project/ros/scripts   six_dof_arm_description/
cp -r robotic_arm_project/src           six_dof_arm_description/   # kinematics.py etc.
chmod +x six_dof_arm_description/scripts/*.py

# 2. Add `add_service_files(FILES SolveIK.srv)` and
#    `generate_messages(DEPENDENCIES geometry_msgs)` to CMakeLists.txt
#    (standard catkin service-generation boilerplate)

# 3. Build
cd ~/catkin_ws && catkin_make && source devel/setup.bash
```

### Run the simulation
```bash
roslaunch six_dof_arm_description arm_sim.launch
```
This spawns the arm in **Gazebo** (physics simulation — gravity,
joint dynamics, collisions against the ground plane and any world
objects you add), starts `robot_state_publisher` so **RViz** can show
the live TF tree and 3D model, and loads the
`arm_trajectory_controller` (a `position_controllers/JointTrajectoryController`)
that accepts pre-planned trajectories.

### Execute the planned path on the simulated robot
```bash
# First, generate the trajectory offline (already done if you ran demo.py):
cd robotic_arm_project/src && python3 demo.py

# Then stream it to the running Gazebo/RViz simulation:
rosrun six_dof_arm_description trajectory_publisher_node.py \
    _csv_path:=/absolute/path/to/robotic_arm_project/output/trajectory.csv
```
This reads `trajectory.csv` and sends it as a single
`FollowJointTrajectory` action goal — the arm in Gazebo will execute the
exact collision-free, smooth motion computed in `src/demo.py`, and you
can watch it in RViz.

### On-demand IK
```bash
rosservice call /solve_ik "{target_xyz: {x: 0.35, y: 0.35, z: 0.15}, seed_joint_angles: []}"
```
calls `ik_service_node.py`, which wraps the exact same
`SixAxisArm.inverse_kinematics()` used by the standalone simulation.

### Why split it this way
Planning (IK + RRT + spline fitting) is pure math — it doesn't need a
physics engine, and iterating on it is much faster as plain Python you
can run/plot/debug directly (as done throughout this project) than
inside a full ROS+Gazebo loop. Execution (actually moving a simulated or
real robot, respecting real controller/hardware timing) does need
ROS/Gazebo. Keeping them separate — with `trajectory.csv` as the
interface — means the planning code is portable to any robot stack (or
no ROS at all), and the ROS layer stays thin.

## 4. Key files at a glance

| File | Role |
|---|---|
| `src/kinematics.py` | `SixAxisArm` class: DH-based FK, geometric Jacobian, damped-least-squares IK |
| `src/collision.py` | `SphereObstacle`, `CollisionChecker`: link-capsule vs obstacle-sphere checks |
| `src/rrt_planner.py` | `RRTPlanner`: joint-space RRT + path shortcutting |
| `src/trajectory_planning.py` | `TrajectoryPlanner`: quintic spline fit + sampling |
| `src/demo.py` | End-to-end pipeline; produces all files in `output/` |

| `ros/scripts/ik_service_node.py` | ROS service wrapper around the IK solver |
| `ros/scripts/trajectory_publisher_node.py` | Streams `trajectory.csv` to the robot's controller |

## 5. Known limitations / next steps
- The IK solver is numerical, not closed-form — it's general-purpose but
  slower and can converge to different elbow configurations depending on
  the seed (handled here by trying several seeds and rejecting colliding
  solutions; see `solve_ik_collision_free()` in `demo.py`).
- Obstacles are spheres only; extending `collision.py` with boxes/meshes
  (e.g. via `trimesh` or Gazebo's own collision geometry) would let it
  model real-world scenes more precisely.
- RRT is not RRT\*, so paths are collision-free but not
  optimal-length; the shortcutting step mitigates this significantly in
  practice.
- The ROS package files are provided complete and consistent with each
  other, but were authored and reviewed without a live ROS install to
  build/run against — double-check them against your specific ROS
  distro's API when you build the catkin package.
